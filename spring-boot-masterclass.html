Spring Framework & Spring Boot Masterclass

From Java Fundamentals to Enterprise Architecture with current Spring standards
Java 21 / Spring 6.x → 7.x / Spring Boot 3.x → 4.x / Boot 3.5 / Cloud Native / Microservices / Security / Kafka
flowchart TD A[Java Fundamentals] --> B[Spring Core] B --> C[Spring MVC] C --> D[Spring Boot] D --> E[Spring Data] E --> F[Security] F --> G[Testing] G --> H[Production] H --> I[Microservices] I --> J[Distributed Systems] J --> K[Cloud Native] K --> L[Performance] L --> M[Architecture] M --> N[Enterprise Architecture]

This tutorial is designed for a Java developer with 13+ years of experience who wants to understand not just how to use Spring, but why Spring works this way, how the internals fit together, when to use or avoid each pattern, and how to defend architecture choices under production and interview pressure.

What mattersWe prioritize current official Spring documentation and version-aware guidance. We do not mix old and new APIs in the same example. We explicitly show what is current, legacy, deprecated, removed, and version-specific.

Version designations and correctness

Current

Spring Framework 6.2.x / 7.x, Spring Boot 3.3-3.5+, Java 17-21 LTS, Jakarta EE namespaces, Boot 3 current standard for new greenfield work.

Legacy

Spring 5 / Boot 2, Java 8/11, javax.* APIs, older servlet/container integrations.

Deprecated

Some XML configuration patterns and old security config classes are still in docs for migration guidance but not recommended for new apps.

Removed

Old `WebSecurityConfigurerAdapter` patterns, some old servlet APIs, older security setup classes, and some XML-specific approaches are removed in modern Boot 3+/6+.
Why old versions still existCompanies often keep older Spring versions because of framework freeze, legacy container support, deeper Java 8/11 compatibility, regulatory constraints, or long-lived enterprise apps. Upgrading is not just a library bump; it changes the Java baseline, JPA API, validation API, security rules, servlet APIs, and deployment assumptions.

03 · Spring Fundamentals

what/why/how

What is Spring?

Spring is a framework for Java applications that reduces boilerplate, encourages POJO-based development, and gives a consistent ecosystem around dependency injection, transactions, web MVC, security, data access, and testing. It was created to solve the complexity of Enterprise Java (EJB, heavy XML configuration, rigid lifecycle, difficult testability).

Problems with traditional Java EE

Monolithic EJB APIs, container coupling, heavy XML descriptors, poor testability, difficult mocking, and high operational complexity.

Problems with EJB

Large component model, deployment overhead, remote/local interfaces, poor unit testability, and too much infrastructure in the application layer.

Spring philosophy

POJOs over legacy enterprise APIs. Dependency injection over hard-coded wiring. Declarative transactions over manual commits. AOP to separate cross-cutting concerns. Convention over configuration with Boot.

Core idea

Instead of classes creating their own dependencies, the framework creates and assembles object graphs. The application focuses on business behavior while Spring handles object lifecycle and wiring.
ApproachMain ideaStrengthsWeaknesses
Traditional JavaManual object creation and wiringPredictableHigh coupling and low testability
SpringContainer manages object graph and lifecycleLoosely coupled, powerful ecosystemNeed to understand lifecycle and proxy behavior
Spring BootSpring + opinionated defaults + starters + auto-configFast startup, easier developer experienceLess explicit control; hidden behavior sometimes surprises teams

04 · Inversion of Control

core concept

IoC means control of object creation and lifecycle is inverted from your application code to a framework or container. Dependency Injection is the main mechanism by which IoC is achieved.

flowchart LR A[Application Code] --> B[Dependency Lookup] A --> C[Dependency Injection] C --> D[Container creates and wires objects] B --> E[Manual lookup from factory/context]

Dependency Injection

Dependencies are provided externally rather than built with `new` inside the class.

Dependency Lookup

Object asks a container or factory for dependencies. Service Locator pattern is an example of this older style.

Constructor injection

Dependencies are passed in the constructor; immutable and easy to test.

Setter injection

Dependencies are set after object construction; useful for optional dependencies but less explicit.
class OrderService {
    private final PaymentService paymentService;

    OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

Spring creates the `PaymentService`, creates an `OrderService` instance, and injects the dependency at bean creation time. This is why constructor injection is preferred in modern Spring apps: it enforces required dependencies, supports immutability, and makes tests simpler.

Why constructor injection wins1. Required dependencies are explicit. 2. Object is valid immediately after construction. 3. Easier unit testing and mocking. 4. Better for immutability and thread safety. 5. Works well with final fields and modern design.
TypeProsConsRecommendation
Field injectionConciseHidden dependencies, harder to test, not finalAvoid in production
Setter injectionFlexible and optionalMutability, less clear lifecycleUse for optional configuration only
Constructor injectionClear, immutable, testableMore boilerplatePreferred

05 · Spring Container

internals
flowchart TD A[Application] --> B[ApplicationContext] B --> C[Bean Definitions] C --> D[Bean Creation] D --> E[Dependency Injection] E --> F[Bean Lifecycle] F --> G[Application Ready]

The Spring container is the runtime environment responsible for managing beans and their dependencies. It reads configuration metadata, builds object graphs, invokes lifecycle callbacks, and populates the application context.

BeanFactory

Low-level container, minimal functionality, lazy loading. Good for lightweight infrastructure, but less rich than ApplicationContext.

ApplicationContext

Full-featured container used by most apps. Adds internationalization, resource loading, event handling, BeanPostProcessor integration, and richer lifecycle support.

GenericApplicationContext

Flexible, generic container used for non-web apps and custom setup.

AnnotationConfigApplicationContext

Loads configuration classes annotated with `@Configuration`, scanning packages and registering beans.

WebApplicationContext

Servlet-based application context used by Spring MVC and web apps.

What happens internally

Read `@Configuration`; parse bean definitions; build metadata; instantiate beans; call `BeanFactoryPostProcessor`; execute `BeanPostProcessor`s; inject properties and dependencies; invoke lifecycle methods; publish context ready events.
AnnotationConfigApplicationContext context =
    new AnnotationConfigApplicationContext(AppConfig.class);

OrderService orderService = context.getBean(OrderService.class);
context.close();

06 · Spring Beans

bean lifecycle
flowchart TD A[Bean Definition] --> B[Instantiation] B --> C[Dependency Injection] C --> D[Aware Interface Callbacks] D --> E[BeanPostProcessor beforeInit] E --> F[@PostConstruct] F --> G[Initialization] G --> H[BeanPostProcessor afterInit] H --> I[Bean Ready] I --> J[@PreDestroy] J --> K[Destroy]

A Spring bean is a singleton-like managed object created by the container and controlled by Spring lifecycle. It is not the same as the Java Singleton pattern — a Spring singleton means one shared bean instance per Spring container, while a Java Singleton is a JVM-wide singleton enforced by your own coding pattern.

ScopeMeaningUse when
singletonOne instance per application contextDefault for stateless services
prototypeNew instance each request for beanStateful or short-lived objects
requestOne instance per HTTP requestWeb applications
sessionOne instance per HTTP sessionUser session scoped objects
applicationOne instance per ServletContextShared web app state
websocketOne instance per WebSocket sessionWebSocket app state
@Component
@Scope("prototype")
class ShoppingCart { }

@Component
class CheckoutService {
    private final ShoppingCart shoppingCart;

    CheckoutService(ShoppingCart shoppingCart) {
        this.shoppingCart = shoppingCart;
    }
}

Spring does not magically make a bean singleton in the Java sense; it creates and manages one bean object per scope per container, and the scope semantics matter for proxies and thread safety.

07 · Configuration Styles

XML vs Java vs annotations

XML configuration

Classic Spring style using `` declarations. Common in old enterprise apps and migration work. Example: old `.xml` config with `DataSource`, `TxManager`, `BeanFactory` definitions.

Java configuration

`@Configuration` + `@Bean`. Very explicit, good for complex infrastructure and external library integration.

Annotation configuration

`@Component`, `@Service`, `@Repository`, `@Controller`, `@RestController`, `@Configuration`, plus component scanning. Most common modern style.

Modern pattern

Use Boot auto-configuration + component scanning + `@ConfigurationProperties` + class-based configuration. Avoid XML unless you are maintaining legacy services.
// Java config
@Configuration
public class AppConfig {

    @Bean
    public PaymentService paymentService() {
        return new CardPaymentService();
    }
}
// XML legacy
<beans>
    <bean id="paymentService" class="com.bank.CardPaymentService"/>
    <bean id="orderService" class="com.bank.OrderService">
        <constructor-arg ref="paymentService"/>
    </bean>
</beans>
When XML is still encounteredLegacy enterprise systems, older Spring apps in regulated industries, legacy integration layers, or migration work where the team is actively refactoring from XML to Boot. The main risk is losing explicit lifecycle visibility and making the configuration harder to reason about.

08 · Component Scanning

@ComponentScan

Component scanning tells Spring “look in these packages and register classes as beans”. It is how `@Component`, `@Service`, `@Repository`, `@Controller`, and `@Configuration` classes become managed beans automatically.

@Configuration
@ComponentScan(basePackages = "com.bank")
public class AppConfig {}

@Component

Generic bean stereotype.

@Service

Business service layer.

@Repository

Persistence layer and exception translation.

@Controller

Web MVC controller.

@RestController

Controller + `@ResponseBody` convenience.

@Configuration

Configuration class defining beans and metadata.

Spring scans package roots, reads metadata, filters candidates, and registers them as bean definitions. The scan uses include/exclude patterns to avoid accidentally bringing in infrastructure classes, test classes, or shadow parent packages.

Common mistakesScanning the entire application root too broadly; missing base packages; accidentally scanning test code into production; placing `@Configuration` classes in the wrong package; relying on implicit component scanning in large multi-module apps.

09 · Autowiring

DI resolution

Autowiring asks Spring to resolve and inject collaborators automatically. Modern production code should generally prefer constructor injection over field injection, even when `@Autowired` is available.

interface PaymentService {}

@Service
class CardPaymentService implements PaymentService {}

@Service
class UpiPaymentService implements PaymentService {}

@Service
class OrderService {
    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

If there are multiple beans implementing the same interface, Spring cannot decide automatically unless you specify a primary or qualifier. This is a perfect example of the container’s resolution logic.

@Qualifier

Pick the exact bean by name or qualifier value.

@Primary

Default candidate when multiple beans match.

Optional dependencies

Can be injected as `Optional` or `@Autowired(required = false)` in older patterns.

Multiple beans

Spring resolves collections like `List` or `Map`.
@Service
@Qualifier("card")
class CardPaymentService implements PaymentService {}

@Service
@Qualifier("upi")
class UpiPaymentService implements PaymentService {}

@Service
class PaymentProcessor {
    private final PaymentService paymentService;

    PaymentProcessor(@Qualifier("card") PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

environment-specific config

Profiles let the same application behave differently in development, testing, QA, and production. The environment is selected by property, system property, environment variables, or launcher setting.

@Profile("dev")
@Configuration
class DevSecurityConfig { }

@Profile("prod")
@Configuration
class ProdSecurityConfig { }

11 · Externalized Configuration

properties, YAML, env

@Value

Simple property injection for a few values.

Environment

Platform-aware access to property sources and profiles.

PropertySource

Custom property definitions from files, systems, vaults, or maps.

@ConfigurationProperties

Strongly typed grouping of configuration values for large apps.
@ConfigurationProperties(prefix = "app.payment")
public class PaymentProperties {
    private String gatewayUrl;
    private Duration timeout;
    private String apiKey;
}

For large applications, `@ConfigurationProperties` is better than `@Value` because it is type-safe, grouped, namespaced, documentable, and easier to validate. A single `@Value` per field becomes painful in large systems.

app:
  payment:
    gateway-url: https://payments.acme
    timeout: 5s
    api-key: ${PAYMENT_API_KEY}
PrecedenceCommand-line args > OS environment variables > external config files > application defaults > bundled defaults. There are many layers, and production teams should understand the exact precedence order to avoid “works on my machine” failures.

12 · Spring Expression Language (SpEL)

expressions

SpEL lets Spring evaluate expressions at runtime, which is useful in security, configuration, and bean wiring. It supports method invocation, property access, relational logic, collection access, and conditional logic.

@Value("#{systemProperties['user.country']}")
private String country;

@Value("#{order.total > 1000 ? 'VIP' : 'STANDARD'}")
private String customerTier;

It is used in modern Spring Security expressions and configuration, but it should not be overused for business logic. Keep business rules in normal Java code rather than magical strings.

13 · AOP

cross-cutting concerns
flowchart LR A[Client] --> B[Proxy] B --> C[Advice] C --> D[Target Object]

Aspect-Oriented Programming handles cross-cutting concerns such as logging, transaction boundaries, security, metrics, and auditing without scattering them through business code. Spring AOP is proxy-based and usually applied to Spring-managed beans.

Aspect

A modular unit encapsulating cross-cutting logic.

Join point

Specific execution point such as method invocation.

Pointcut

Expression that selects join points.

Advice

Action executed before/after/around a join point.

Proxy

Intercepting object that adds behavior.

Target

The actual business object.
@Aspect
@Component
class LoggingAspect {
    @Before("execution(* com.bank.service.*.*(..))")
    public void logBefore() {
        System.out.println("Calling service method...");
    }
}

Spring AOP uses JDK dynamic proxies for interfaces and CGLIB for class-based proxies. The self-invocation problem is important: a method calling another method on the same bean does not trigger the proxy, so AOP advice may not run as expected.

Self-invocation problemIf `methodA()` calls `methodB()` on the same bean, the AOP proxy does not intercept the internal call. For transactions, this is a frequent cause of surprising behavior. Use external service boundaries or `@Transactional` at the service layer, not inside the same class.

14 · Transactions

deep dive
flowchart LR A[Transactional Method] --> B[Spring Proxy] B --> C[TransactionInterceptor] C --> D[PlatformTransactionManager] D --> E[Database]

Transactions guarantee atomicity, consistency, isolation, and durability (ACID) for business operations. In Spring, the transaction boundary is often the service layer. Annotations make declarative transaction management easy, but correct usage requires understanding propagation and rollback rules.

PropagationMeaningTypical Use
REQUIREDJoin existing transaction or start new oneDefault; most business operations
REQUIRES_NEWAlways start a new transactionAudit, notifications
NESTEDNested savepoint-based transactionSpecific DB support needed
SUPPORTSRun within transaction if one existsRead-only ops
NOT_SUPPORTEDExecute without transactionBatch or read-only non-transactional work
MANDATORYMust be called with existing transactionAPI contract enforcement
NEVERMust not run within existing transactionStrict separation
@Transactional
public void transferFunds(Long fromId, Long toId, BigDecimal amount) {
    // debit account
    // credit account
    // persist audit event
}

Rollback rules: unchecked exceptions (`RuntimeException`, `Error`) cause rollback by default; checked exceptions do not unless configured. The `rollbackFor` and `noRollbackFor` attributes are used when a business-specific checked exception should trigger rollback or not.

Isolation

READ_UNCOMMITTED, READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE. Higher isolation reduces anomalies but increases lock contention.

Dirty read

One transaction reads uncommitted data from another. Avoid with higher isolation.

Non-repeatable read

Rows change between reads in the same transaction.

Phantom read

New rows appear due to concurrent inserts during a range query.
Common transaction mistakesNot placing `@Transactional` at the service layer; using too broad boundaries; calling a method from inside the same class; using `REQUIRES_NEW` in loops without considering performance; Hidden DB-level locks; mismatched rollback semantics.

15 · Spring MVC

web stack
flowchart TD A[Client] --> B[HTTP Request] B --> C[DispatcherServlet] C --> D[HandlerMapping] D --> E[Controller] E --> F[Service] F --> G[Repository] G --> H[Database] H --> I[Response to Client]

Spring MVC is a request-driven web framework built around the `DispatcherServlet`, which dispatches to controllers, handles method arguments, resolves views, converts request/response data, and manages exception flow.

DispatcherServlet

Main front controller for HTTP requests.

HandlerMapping

Map request to handler method.

HandlerAdapter

Invoke the controller method with the right signature.

ViewResolver

Resolve view names to actual templates.

HttpMessageConverter

Convert JSON/XML to objects and vice versa.

ExceptionResolver

Convert exceptions into HTTP responses.

16 · REST APIs

HTTP design

REST is about resources, stateless interactions, standard HTTP methods, and meaningful representations. In production, careful API design matters more than a clever framework.

MethodIntentIdempotency
GETRead resourceYes
POSTCreate new resource / commandNo
PUTReplace or upsert resourceYes
PATCHPartial updateUsually not guaranteed
DELETEDelete resourceUsually yes with proper semantics
@PostMapping("/customers")
public ResponseEntity createCustomer(@Valid @RequestBody CustomerRequest request) {
    CustomerResponse response = customerService.create(request);
    return ResponseEntity.status(HttpStatus.CREATED).body(response);
}

In enterprise APIs, use DTOs instead of exposing JPA entities directly. Keep API contracts stable, validate incoming payloads, return consistent error envelopes, and provide correct idempotency keys or deduplication semantics for payment or order creation endpoints.

17 · Validation

Jakarta Validation

Validation ensures that incoming data is acceptable before it reaches business logic. Spring Boot 3 uses Jakarta Validation and Bean Validation APIs.

@Data
public class CustomerRequest {
    @NotBlank
    private String name;

    @Email
    private String email;

    @Size(min = 8, max = 30)
    private String password;
}

Use `@Valid` or `@Validated` on controller parameters. For APIs, centralize validation errors into a standard response such as:

{
  "timestamp": "2026-08-15T01:49:35Z",
  "status": 400,
  "error": "Validation Failed",
  "message": "Request validation failed",
  "path": "/api/customers",
  "errors": [
    {"field":"email","message":"must be a well-formed email address"}
  ]
}
RuleValidate at boundaries, not everywhere. Validate HTTP input and domain invariants, but keep domain rules in domain services.

18 · Exception Handling

global error handling

Exception handling is one of the most important parts of production-grade API design. Business exceptions should be specific, consistent, and secure. Do not leak database errors or stack traces to clients.

@RestControllerAdvice
public class ApiExceptionHandler {
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity handleValidation(MethodArgumentNotValidException ex) {
        return ResponseEntity.badRequest().body(ApiErrorResponse.validation(ex));
    }

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity handleNotFound(ResourceNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(ApiErrorResponse.notFound(ex.getMessage()));
    }
}

@ExceptionHandler

Method-level exception mapping.

@ControllerAdvice

Shared for MVC controllers.

@RestControllerAdvice

Best choice for JSON APIs.

ResponseEntityExceptionHandler

Extends common default exception handling.

19 · Spring Data

repositories & JDBC

Spring JDBC

Low-level template abstraction over JDBC.

JdbcTemplate

Used for direct SQL and persistent operations when you want control.

NamedParameterJdbcTemplate

More readable SQL with named parameters.

Spring Data JPA

Repository abstraction with query derivation, paging, sorting, and custom query support.
public interface CustomerRepository extends JpaRepository {

Spring Data hides much of the boilerplate but still relies on JPA/Hibernate for object mapping. For complex queries, prefer repository methods, `@Query`, projections, and query DSLs; use raw SQL only where required for performance or database-specific behavior.

20 · JPA / Hibernate

deep dive
flowchart TD A[Entity] --> B[Persistence Context] B --> C[First-Level Cache] C --> D[Dirty Checking] D --> E[Flush] E --> F[Commit] F --> G[Database]

JPA manages persistence with entities, an EntityManager, and a persistence context. Hibernate is the implementation used by most Spring Data JPA setups.

Entity

Mapped Java class representing a database table.

EntityManager

Interface for persistence operations.

Persistence context

A first-level cache containing managed entities.

Dirty checking

Hibernate detects changes to managed entities before flush.

Flush

Synchronize persistence context state with database

Commit

Finalize transaction and flush if needed

Entity lifecycle is transient → managed → detached → removed. Lazy loading means a relation is loaded only when accessed, while eager loading prefetches it; both have trade-offs for performance and risk of N+1 issues.

21 · JPA Relationships

entity design
RelationshipMeaningCommon issues
@OneToOneSingle record to single recordUnnecessary eager fetch; ownership confusion
@OneToManyParent to many childrenN+1, oversized collections, cascade misuse
@ManyToOneMany children to single parentLazy loading causing N+1 if accessed poorly
@ManyToManyMany-to-many join tableHard to model and manage; usually should be factored

The owning side controls the foreign key. `mappedBy` indicates the inverse side. `cascade` propagates persistence operations; `orphanRemoval` removes child rows when the relationship is severed. Fetch strategies matter: eager usually causes unnecessary data reads while lazy may cause N+1 if not planned carefully.

N+1 problemCommon when a parent list is loaded and then each child is lazily loaded separately. Fix by `JOIN FETCH`, `EntityGraph`, batch fetching, fetch joins, or DTO projections.
@Entity
public class Order {
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List items = new ArrayList<>();
}

@Entity
public class OrderItem {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id")
    private Order order;
}

22 · Database Transactions and Performance

production data layer

Connection pooling

HikariCP is the default in Spring Boot for efficient DB connection management.

Indexes

Proper indexes reduce scan cost and support joins and sorting.

Pagination

Never fetch all rows into memory if they are large.

Optimistic locking

Version columns; excellent for low contention.

Pessimistic locking

Explicit row locks; use carefully under high contention.

Query tuning

Use explain plans, avoid `SELECT *`, filter early, join appropriately.

Connection pool sizing is not arbitrary. It is based on DB capacity, query latency, number of threads, and expected concurrency. Underprovisioning means queueing and timeouts; overprovisioning causes lock contention and DB pressure.

spring.datasource.hikari.maximum-pool-size=20
spring.datasource.hikari.minimum-idle=10
spring.datasource.hikari.connection-timeout=30000

23 · Spring Boot

opinionated framework

Spring Boot removes much of the boilerplate and configuration friction. It provides opinionated defaults, dependency management, starter packages, embedded servers, health endpoints, auto-configuration, and a faster developer experience.

@SpringBootApplication
public class PaymentServiceApplication {

It is built on top of the Spring Framework but adds a runtime startup path. `@SpringBootApplication` is equivalent to three pieces:

@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan

Marks the class as the application configuration entry point.

@EnableAutoConfiguration

24 · Auto-configuration

Spring Boot internals

Auto-configuration decides which beans should exist based on classpath, environment, conditional classes, and user beans. It is one of the reasons Spring Boot feels magical without being opaque.

@Configuration
@ConditionalOnClass(DataSource.class)
@ConditionalOnProperty(name = "spring.datasource.url")
class DataSourceAutoConfiguration {}

57 · Interview Preparation

questions by level
What is IoC and how is it different from DI?Q1

IoC is the inversion of control of object creation and lifecycle. Dependency injection is a specific way to implement IoC by supplying dependencies from the outside. In Spring, the container is responsible for creating and wiring beans while application code focuses on behavior.

How does Spring create beans and inject dependencies?Q2

Spring reads configuration metadata, creates bean definitions, instantiates beans, resolves dependencies, runs lifecycle callbacks, and registers them in the application context. Constructor injection is the most explicit and preferred pattern.

Why does `@Transactional` fail when called internally inside the same bean?Q3

Spring transaction behavior is implemented through proxies. Internal self-invocation bypasses the proxy, so transactional advice is not triggered. The fix is to move the transactional boundary to a different bean or call through a service boundary.

What is bean scope and how does it differ from Java Singleton?Q4

Bean scope defines the lifecycle of a Spring-managed object within the container. Singletons are container-scoped; Java singleton is a class-level design pattern that enforces one instance per classloader. They are related but not the same concept.

Top architect questionHow would you design a highly available Spring Boot platform? Answer: clear boundaries, stateless services, externalized config, retries with timeouts, observability, database-per-service, Kafka for decoupling, API gateway, proper secrets management, autoscaling, and deployment discipline.

58 · Troubleshooting Playbook

production diagnosis

Application won't start

Symptoms: context startup failure, bean creation exceptions. Diagnose with logs, stack trace, component scan, missing properties, and dependency mismatches. Fix by validating configuration, versions, dependencies, and bean classpath conditions.

Bean creation error

Check missing dependency, circular dependency, qualifier mismatch, and profile conditions. Review logs and use `@Primary` or explicit `@Qualifier` if needed.

OutOfMemoryError

Collect heap dump, analyze leak suspects, inspect GC logs, and review object retention patterns. Reduce caching, close resources, and avoid large object retention in thread locals or static collections.

Slow API

Check DB latency, CPU saturation, GC pauses, thread pool exhaustion, N+1 queries, and network issues. Add SQL explain plans and request tracing.

Database timeout

Often caused by failing connection pool or slow SQL. Check Hikari settings, pool usage, DB load, locks, indexes, and query plans.

Kafka lag

Inspect consumer throughput, partition count, processing time, dead-letter topics, retry loops, and stateful consumer logic.
