01 · Microservices Fundamentals

foundation
graph LR A[Monolith] --> B[Modular Monolith] --> C[SOA] --> D[Microservices] --> E[Cloud-Native Distributed Systems]

What is a monolith?

A single deployable unit containing all business capabilities — Order, Payment, Inventory logic all compiled, deployed, and scaled together against one database.

Problems with monoliths at scale

Every change requires a full redeploy; one team's bug can crash unrelated features; the whole app scales even if only one module is hot; the codebase grows harder to reason about as headcount grows.

Modular monolith

Same single deployable, but with enforced internal module boundaries (package-private APIs, no cross-module table access). Often the right first step before microservices — you get boundary discipline without distributed-systems cost.

SOA vs Microservices

SOA centralizes integration logic in an Enterprise Service Bus and often shares a canonical data model; microservices push integration logic to the edges (smart endpoints, dumb pipes) and insist on independent data ownership per service.

Conway's Law & organizational impact

Conway's Law"Organizations design systems that mirror their own communication structure." In practice: if Order, Payment, and Inventory are owned by three separate teams, you'll naturally get three separate services — and if you try to force a different architecture than your team structure, the architecture loses. Team ownership boundaries and service boundaries should be designed together, not independently.
MonolithMicroservices
DeploymentOne unit, one pipelineIndependent per service
ScalingScale the whole appScale only the hot service
Data ownershipUsually one shared schemaDatabase-per-service
Failure blast radiusOne bug can take down everythingIsolated, if resilience patterns are applied
Operational complexityLowHigh — needs observability, service discovery, orchestration
Team autonomyLow — shared codebase, coordinated releasesHigh — independent release cadence per team
When NOT to use microservicesSmall team (fewer than ~8–10 engineers), unclear or rapidly-changing domain boundaries, low traffic that doesn't need independent scaling, or a team without operational maturity in containers/observability/on-call. Microservices trade development simplicity for operational flexibility — that trade is not free, and a distributed monolith (all the deployment complexity, none of the independence) is worse than the monolith you started with.

Microservices maturity model

Level 0: monolith. Level 1: modular monolith with clear internal boundaries. Level 2: a handful of coarse-grained services split along clear bounded contexts. Level 3: full microservices with independent databases, CI/CD, and on-call ownership per team. Level 4: event-driven, cloud-native, self-healing, observable at the SLO level. Most organizations should stop advancing a level before they think they should — premature Level 3/4 adoption is the most common cause of the "distributed monolith" anti-pattern.

02 · Designing Microservices — DDD & Boundaries

foundation

Bounded Context

A boundary within which a domain model and its terminology are consistent. "Customer" in the Order context (shipping address, order history) is a different model than "Customer" in the Marketing context (segments, campaigns) — forcing one shared "Customer" entity across both is where shared-database pain begins.

Aggregates, Entities, Value Objects

An Aggregate (e.g. Order + its OrderLines) is a consistency boundary — changes inside it are transactional; changes across aggregates are eventual. An Entity has identity and a lifecycle (Order). A Value Object has no identity, only value (Money, Address) and is immutable.

Domain Services vs Application Services

A Domain Service holds business logic that doesn't naturally belong to one entity (e.g. pricing rules spanning several products). An Application Service orchestrates use cases — calling domain logic, repositories, and publishing events — but holds no business rules itself.

Anti-Corruption Layer

A translation layer at a service boundary that converts an external or legacy model into your own bounded context's model, preventing another team's (or a legacy system's) domain concepts from leaking in and corrupting yours.

Bad design: shared database

graph TD CS[Customer Service] --> DB[(Shared Oracle DB)] OS[Order Service] --> DB PS[Payment Service] --> DB
Why this is dangerousAny service can read or write any other service's tables, so schema changes become cross-team coordination events; a slow query in Payment Service can lock rows Order Service needs; there's no way to reason about which service "owns" a piece of data; and it becomes a distributed monolith — you pay for the operational cost of microservices while keeping the tight coupling of a single database.

Better design: database-per-service

graph LR CS[Customer Service] --> CDB[(Customer DB)] OS[Order Service] --> ODB[(Order DB)] PS[Payment Service] --> PDB[(Payment DB)]

Each service owns its schema exclusively — no other service ever queries it directly. Cross-service data needs are satisfied through the service's API or through events, not through a JOIN. This is the single most important structural rule in microservices design: if you can still JOIN across two services' tables, they are not actually separate services.

5–11. Entity, DTO, repository, service, controller, exceptions, validation
@Entity @Table(name = "ORDERS")
class Order {
    @Id @GeneratedValue UUID id;
    String customerId;
    @Enumerated(EnumType.STRING) OrderStatus status;
    @OneToMany(cascade = CascadeType.ALL, orphanRemoval = true)
    List<OrderLine> lines;
    BigDecimal totalAmount;
    Instant createdAt;
}

// DTO as a Java 21 record — immutable, concise
record CreateOrderRequest(
    @NotBlank String customerId,
    @NotEmpty List<OrderLineRequest> lines) {}

@Service
class OrderApplicationService {
    private final OrderRepository orderRepository;
    private final OutboxRepository outboxRepository; // see Part 14 — Outbox

    OrderApplicationService(OrderRepository orderRepository, OutboxRepository outboxRepository) {
        this.orderRepository = orderRepository; this.outboxRepository = outboxRepository; // constructor injection
    }

    @Transactional
    public Order createOrder(CreateOrderRequest request) {
        Order order = Order.from(request);
        orderRepository.save(order);
        outboxRepository.save(OutboxEvent.of("Order", order.getId(), "OrderCreated", order));
        return order;
    }
}

@RestController @RequestMapping("/api/v1/orders")
class OrderController {
    @PostMapping
    ResponseEntity<OrderResponse> create(@Valid @RequestBody CreateOrderRequest req) {
        Order order = orderApplicationService.createOrder(req);
        return ResponseEntity.created(URI.create("/api/v1/orders/" + order.getId()))
            .body(OrderResponse.from(order));
    }

    @ExceptionHandler(OrderNotFoundException.class)
    ResponseEntity<ProblemDetail> handleNotFound(OrderNotFoundException ex) {
        return ResponseEntity.status(404).body(ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage()));
    }
}

05 · Spring Boot Production Architecture

developer

Auto-configuration & DI

Spring Boot inspects the classpath and configures beans conditionally (@ConditionalOnClass, etc). Constructor injection is preferred over field injection — it makes dependencies explicit, immutable, and trivially mockable in tests.

Profiles & externalized config

application.yml + application-{profile}.yml, overridden by environment variables in each deployment target — never hardcode environment-specific values, and never commit secrets to the config file itself.

Actuator & health endpoints

/actuator/health aggregates health indicators (DB, Kafka, disk space); split into liveness and readiness groups so Kubernetes probes each independently (see Part 22).

Graceful shutdown

server.shutdown=graceful lets in-flight requests finish before the JVM exits — critical during rolling deployments so users don't see dropped connections mid-request.

07 · API Gateway

developer
sequenceDiagram participant C as Client participant G as API Gateway participant A as Auth Server participant O as Order Service C->>G: POST /api/v1/orders (JWT) G->>A: validate token (or local JWKS check) A-->>G: valid, claims G->>G: rate limit check, add Correlation-Id G->>O: forward request O-->>G: 201 Created G-->>C: 201 Created

An API Gateway (Spring Cloud Gateway) centralizes cross-cutting edge concerns so individual services don't each reimplement them: routing, authentication/token validation, coarse rate limiting, request/response transformation, CORS, SSL termination, and correlation-ID injection. It's a single well-known entry point — and, deliberately, a single circuit-breaking layer that can shed load before it reaches overloaded backend services.

          filters:
            - name: CircuitBreaker
              args:
                name: orderServiceCB

            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 100
                redis-rate-limiter.burstCapacity: 200
Architect noteDon't put business logic in the gateway. Its job is routing and cross-cutting policy enforcement — the moment it starts making business decisions, it becomes a hidden, hard-to-test extension of every downstream service, and a single point of coupling that undermines service independence.

gRPC is a synchronous option like REST but with a binary protocol (Protobuf) and generated strongly-typed stubs — lower latency and payload size than JSON/REST, at the cost of less human-readable debugging and less universal client tooling than REST.

Architect decision ruleChoose synchronous when the caller genuinely cannot proceed without an answer right now (checking real-time inventory before confirming a purchase). 10 · Event-Driven Architecture

advanced

Event notification

A thin event ("OrderCreated, id=123") tells subscribers something happened; they call back to fetch details if needed. Minimizes coupling to a shared payload shape, at the cost of an extra round-trip.

Event-carried state transfer

The event carries the full data subscribers need ("OrderCreated" with the whole order payload) — avoids the callback round-trip, at the cost of a larger, more tightly-coupled event contract.

Event sourcing

The sequence of events is the source of truth; current state is derived by replaying them. Powerful audit trail and time-travel debugging, but a real architectural commitment — most services in this platform use events as notifications, not as their system of record.

11 · Database Architecture

advanced

Connection pooling — HikariCP

Reuses DB connections instead of opening one per request. Undersized pools cause request queuing under load; oversized pools can overwhelm the database's own max-connections limit — size the pool against measured concurrency, not guesswork.

Optimistic vs pessimistic locking

Optimistic (a @Version column) assumes conflicts are rare — cheap, fails fast on a real conflict, ideal for low-contention resources. Pessimistic (SELECT … FOR UPDATE) locks the row up front — safer under high contention, but reduces concurrency and risks deadlocks if lock order isn't consistent.

The N+1 problem

Lazy-loading a collection inside a loop fires one query per iteration instead of one batched query. Fix with a JPQL JOIN FETCH, an entity graph, or batch fetching — always verify with SQL logging, not assumption.

Read replicas & sharding

Read replicas offload read-heavy traffic from the primary (with eventual-consistency lag to account for). Sharding splits data across multiple database instances by a shard key (e.g. customerId) when a single instance can't hold or serve the volume — a significant operational step, not a first move.
Isolation levels & deadlocksOracle defaults to READ COMMITTED. A deadlock occurs when two transactions lock resources in opposite order and each waits on the other — the database detects and kills one; the application must retry it. Always acquire locks (rows, tables) in a consistent order across the codebase to avoid this by design rather than by luck.

12 · Distributed Transactions & Saga

advanced

With Order DB, Payment DB, and Inventory DB all independently owned, no single ACID transaction can span all three. Two-Phase Commit (2PC) technically can, but requires a transaction coordinator, holds locks across all participants for the duration, and doesn't tolerate partition failure well — it's rarely used in modern cloud-native systems for exactly that reason.

The Saga Pattern

sequenceDiagram participant O as Order Service participant P as Payment Service participant I as Inventory Service O->>P: Charge payment P-->>O: PaymentCompleted O->>I: Reserve inventory I-->>O: InventoryReservationFailed O->>P: Compensate: Refund payment P-->>O: Refunded O->>O: Mark order Cancelled
Choreography SagaOrchestration Saga
Who drives itEach service, reacting to the previous eventA dedicated saga orchestrator service
CompensationEach service publishes its own compensating eventOrchestrator explicitly calls compensating actions in reverse order
Complexity as steps growGets hard to trace past ~4-5 stepsStays visible and testable, but the orchestrator becomes critical infrastructure
2PC vs Saga2PC gives strong consistency but sacrifices availability during the coordination window and doesn't scale well across many services. Saga gives up strong consistency for eventual consistency plus explicit compensation — the standard trade-off accepted in microservices, because availability and service independence usually matter more than immediate cross-service consistency.

13 · The Outbox Pattern

advanced
The dual-write problem"Save to Oracle" + "publish to Kafka" are two independent operations with no shared transaction. If the Oracle commit succeeds but the Kafka publish fails (broker down, network blip), the order exists with no event ever telling Payment/Inventory about it — a silent, hard-to-detect gap.
graph TD A[Application, one local transaction] --> B[ORDERS table] A --> C[OUTBOX_EVENTS table] C --> D[Outbox Publisher] D --> E[(Kafka)] 
@Entity @Table(name = "OUTBOX_EVENTS")
class OutboxEvent {
    @Id UUID id;
    String aggregateType, aggregateId, eventType;
    @Lob String payload;
    boolean published;
}

@Transactional // one local Oracle transaction — atomic by construction, no distributed transaction needed
public Order createOrder(CreateOrderRequest req) {
    Order order = orderRepository.save(Order.from(req));
    outboxRepository.save(OutboxEvent.of("Order", order.getId(), "OrderCreated", toJson(order)));
    return order; // no Kafka call here at all
}

@Scheduled(fixedDelay = 500)
void publishOutbox() {
    for (var e : outboxRepository.findByPublishedFalse()) {
        kafkaTemplate.send("order-events", e.getAggregateId(), e.getPayload())
            .whenComplete((r, ex) -> { if (ex == null) markPublished(e); });
    }
}

Because both writes happen in the same local Oracle transaction, they're atomic without any distributed transaction protocol. A CDC-based publisher (Debezium tailing the redo log) is an alternative to the polling publisher shown here — same guarantee, different mechanism, discussed further in the Kafka masterclass.

14 · Resilience — Resilience4j

advanced
graph LR Client --> A[Service A] --> B[Service B — unavailable] A -.->|circuit opens, fallback used| Client

Timeout

Bounds how long a caller waits — without one, a slow dependency can hold threads/connections indefinitely and exhaust the caller's own resources.

Retry + exponential backoff + jitter

Retries transient failures; backoff avoids hammering a recovering dependency; jitter (randomized delay) prevents many clients from retrying in synchronized waves (the "thundering herd").

Circuit breaker

After enough failures, stops calling the failing dependency for a cooldown window and fails fast with a fallback instead — protects the caller and gives the dependency room to recover.

Bulkhead

Isolates resources (thread pools, connection pools) per dependency so one slow dependency can't exhaust threads needed to serve calls to a healthy one — named after ship compartments that contain flooding.

Rate limiter

Caps outbound or inbound call rate to protect a downstream dependency (or yourself) from being overwhelmed.

Load shedding & fallback

Deliberately reject excess load (return 503 fast) rather than degrading everyone's latency, and provide a fallback (cached/default response) so a partial failure doesn't become a full outage.
@CircuitBreaker(name = "inventoryService", fallbackMethod = "fallbackCheckStock")
@Retry(name = "inventoryService")
@Bulkhead(name = "inventoryService")
@TimeLimiter(name = "inventoryService")
public CompletableFuture<StockLevel> checkStock(String sku) {
    return CompletableFuture.supplyAsync(() -> inventoryClient.getStock(sku));
}

public CompletableFuture<StockLevel> fallbackCheckStock(String sku, Throwable t) {
    return CompletableFuture.completedFuture(StockLevel.unknown(sku)); // degrade, don't crash
}
Never retry blindlyRetrying a non-idempotent write (e.g. "charge card") without an idempotency key turns a transient network blip into a duplicate charge. Retry is safe by default only for idempotent operations (GET, or writes protected by an idempotency key/unique constraint).

15 · Distributed Systems Problems

expert

Partial failure

In a distributed call, "no response" doesn't tell you whether the operation happened. Unlike an in-process call which either fully succeeds or throws, a network call can fail after the remote side already committed its effect — this ambiguity is the root of almost every distributed-systems design pattern in this course.

Duplicate / lost / out-of-order messages

A retried network call can duplicate an effect; a crash before an ack can lose a message from the caller's point of view even though it landed; parallel delivery paths can reorder related messages — hence idempotency, at-least-once design, and partition keys.

Split brain

A network partition can leave two nodes both believing they're the leader/primary, each accepting writes independently — resolved with consensus protocols (Raft) or fencing tokens, never by "just picking one and hoping."

Clock skew

Wall-clock timestamps across machines aren't reliably ordered — never use "latest timestamp wins" for conflict resolution across services without accounting for skew; prefer logical clocks (vector clocks, Kafka offsets) where order actually matters.

CAP theorem & PACELC

CAPDuring a network Partition, you must choose between Consistency (every read sees the latest write, but may be unavailable) and Availability (always respond, but may serve stale data). You don't get to choose "both" during an actual partition — CAP only constrains behavior during a partition, which is why it's often over-applied to normal-operation trade-offs.

PACELC extends this: even without a Partition (E = Else), you still trade Latency against Consistency in normal operation — a strongly-consistent read across regions is slower than an eventually-consistent local read. Most of this platform's data (Oracle per service) is CP within a service and eventually consistent across services via Kafka — a deliberate, stated trade-off, not an accident.

16 · Caching — Redis

advanced

Cache-aside (lazy loading)

App checks cache first; on a miss, reads the DB and populates the cache. Simple and the most common pattern — cache only holds what's actually been requested.

Read-through / write-through

The cache library itself loads on miss (read-through) or writes to the DB and cache together (write-through) — less app code, tighter coupling to the caching layer.

Write-behind

Writes go to the cache immediately and are asynchronously flushed to the DB — fastest writes, but risks data loss if the cache fails before the flush.

TTL & invalidation

Set a TTL matched to how stale data can tolerably be; explicitly invalidate on write where staleness is unacceptable ("famous last words: cache invalidation is one of the two hard problems in computer science").

Cache stampede

Many requests miss simultaneously (e.g. a popular key just expired) and all hit the DB at once. Mitigate with a short-lived lock around the recompute, or staggered/jittered TTLs.

Cache penetration

Repeated requests for a key that doesn't exist in the DB bypass the cache every time. Mitigate by caching the "not found" result too, with a short TTL.

Cache avalanche

Many keys expire at the same moment (all set with the same TTL at the same time), causing a synchronized DB load spike. Mitigate with randomized TTL jitter.

18 · Observability — Logs, Metrics, Traces

advanced

Logs

Structured (JSON), always including a correlation/trace ID, service name, and level — searchable in aggregate, not just readable per-instance.

Metrics

Micrometer → Prometheus → Grafana. Track the four golden signals per service: latency, traffic, errors, saturation.

Traces

OpenTelemetry propagates a trace ID across every hop — HTTP, Kafka headers included — visualized in Jaeger to see exactly where latency accumulates across a multi-service request.
TermMeaning
SLI (Indicator)A measured metric, e.g. "99th percentile order-creation latency"
SLO (Objective)The internal target for that SLI, e.g. "p99 < 300ms, 99.9% of the time"
SLA (Agreement)The external, often contractual commitment to a customer — usually looser than the internal SLO, leaving margin for error
Architect noteObservability is not optional infrastructure you add "later" — without correlation IDs and distributed tracing designed in from the start, a production incident across 6 services becomes a multi-hour log-grepping exercise instead of a five-minute trace lookup.

20 · Performance Engineering

expert

JVM & GC

Size the heap to the workload, not a default; G1GC is the sane default for most services, ZGC/Shenandoah for very large heaps needing low pause times. Watch GC logs for frequent full GCs — usually an undersized heap or a memory leak, not a GC tuning problem.

Thread pools & connection pools

Undersized pools cause queuing and timeouts under load; oversized pools cause context-switch overhead and can overwhelm a downstream dependency's own pool. Size against measured concurrency and downstream capacity together.

Diagnosing a leak

Take heap dumps under sustained load, compare object counts over time (VisualVM, JFR); a steadily-growing collection (an unbounded cache, an event listener never removed) is the most common culprit.

Load & stress testing

JMeter/Gatling to find the throughput ceiling and the point where latency degrades non-linearly — capacity planning should target comfortably below that knee, not right at it.

28 · System Design Exercises

architect
1. E-commerce platform (the running example, generalized)

NFRs: high read volume on product catalog, bursty write volume on checkout, strict payment consistency. Approach: database-per-service, Redis cache in front of the read-heavy Product Service, Kafka + Outbox for the order lifecycle, Saga for cross-service consistency, circuit breakers at every synchronous boundary.

2. Banking transaction system

Key difference from e-commerce: correctness trumps availability far more strongly — prefer strong consistency within the ledger service, use double-entry bookkeeping as the core data model, and treat every transaction as requiring idempotency keys end-to-end. Event sourcing is a strong fit here (regulatory audit trail is a first-class requirement, not an afterthought).

3. Payment platform

Focus: idempotency keys on every charge request, a state machine per payment (pending → authorized → captured → settled/failed) persisted explicitly rather than inferred, PCI-DSS scope minimization (tokenize card data at the edge, never store raw PANs), and reconciliation jobs against the payment processor's own records as a second line of defense.

4. Food delivery system

Focus: real-time location updates (high-frequency, latency-tolerant — a good fit for Kafka or a lighter pub/sub, not strict durability), geospatial matching of orders to drivers, and a saga spanning restaurant-accept → driver-assign → pickup → deliver with time-bound compensations (auto-cancel/reassign on timeout).

5. Ride-sharing system

Focus: similar geospatial matching to food delivery, plus surge pricing (a read-heavy, frequently-recomputed value best served from a fast cache, not computed per-request from raw data), and strong idempotency on trip state transitions since mobile clients retry aggressively on flaky networks.

6. Notification platform

Focus: a single Notification Service consuming events from every other service (order, payment, shipping) rather than each service independently integrating with email/SMS providers — this centralizes provider failover, rate limiting per channel, and user preference/opt-out enforcement in one place.

7. Order management system

This is the platform built throughout the course — see Parts 3–13 for the full decomposition, Saga design, and Outbox implementation.

8. File processing platform

Focus: S3 as the durable store for raw files, an event (S3 event notification → Kafka, or SQS) triggering processing rather than polling, chunked/streaming processing for large files to bound memory use, and a dead-letter path for files that repeatedly fail processing so they don't block the pipeline.

Answering any of these in an interviewAlways work through: functional requirements → non-functional requirements (the numbers matter — get them stated explicitly) → capacity estimation → service decomposition → data model and ownership → sync vs async communication choices → failure handling → scaling → trade-offs, stated out loud. Interviewers are grading the reasoning path at least as much as the final diagram.

29 · Architect Decision Making & ADRs

architect
The decision frameworkFor every architectural decision: What problem are we solving? What are the alternatives? Why this one? What are the trade-offs? What happens when it fails? How does it scale? How does it affect cost and operations? How hard is it to maintain? Writing the answers down — even briefly — is what separates a defensible architecture decision from a preference.

Example ADR

ADR-014: Use the Outbox Pattern for Order Service event publishing

Status: Accepted
Context: Order Service must publish OrderCreated after committing the order to Oracle. A direct "save then publish" is vulnerable to the dual-write problem.
Decision: Adopt the Outbox Pattern — write the order and an outbox event row in one local transaction; a scheduled publisher ships outbox rows to Kafka.
Alternatives considered: 2PC (rejected — operational complexity, availability cost); CDC/Debezium (deferred — adds Kafka Connect infrastructure not yet justified at current scale); direct publish with manual reconciliation (rejected — reconciliation-as-primary-mechanism is fragile).
Trade-offs: Slight publish latency (polling interval) versus guaranteed atomicity; an extra table and scheduled job to operate.
Revisit when: If publish latency requirements tighten below the polling interval, or if we adopt CDC platform-wide for other reasons.

32 · Production Incident Scenarios

expert
1. Kafka consumer lag suddenly increases

Symptoms: lag metric climbing. Investigate: is production volume actually up, or did consumer count/health drop (rebalances, crashes)? Is one specific partition/consumer disproportionately slow? Is a downstream dependency (Oracle) the real bottleneck? Resolution: fix the actual bottleneck rather than reflexively scaling consumers. Prevention: lag alerting well before user-visible impact, load testing that includes the consumer path.

2. Database CPU reaches 100%

Investigate: slow query log for a new or regressed query, a missing index, connection pool storms, or a batch job overlapping peak traffic. Resolution: kill/optimize the offending query, add the missing index, or move the batch job off-peak. Prevention: query review in code review, index monitoring, staging load tests before large data migrations.

3. API latency increases from 100ms to 5 seconds

Investigate: distributed trace to find which hop actually accumulated the latency — don't assume it's the service that's alerting. Check thread pool exhaustion, GC pauses, and a downstream dependency slowdown that circuit breakers should have contained but perhaps weren't configured for.

4. Payment service is unavailable

Immediate: confirm circuit breakers in dependent services opened correctly (Order Service should degrade gracefully, not cascade-fail). Resolution: restore Payment Service; verify no orders were silently dropped rather than queued for retry via Kafka. Prevention: this is exactly why order acceptance and payment processing are decoupled via events rather than a synchronous blocking call.

5. Duplicate orders are created

Investigate: client-side retry without an idempotency key, or a gateway-level retry policy retrying a POST that actually succeeded. Fix: require and enforce an Idempotency-Key header on order creation, with server-side dedup.

6. Kafka messages are processed twice

Cause: normal at-least-once redelivery after a commit-after-processing crash, or a rebalance mid-processing. Fix: this is expected — verify the consumer is actually idempotent (unique constraint, dedup table) rather than treating the duplicate as a bug to "fix" at the Kafka layer.

7. Redis goes down

Impact: depends entirely on whether services treat Redis as a cache (degrade to DB, slower but correct) or as a hard dependency (outage). Prevention: always design cache access with a fallback path to the source of truth, and alert on elevated DB load as an early signal of cache unavailability.

8. Kubernetes pods continuously restart (CrashLoopBackOff)

Investigate: kubectl describe pod and logs from the previous container instance — commonly a failing liveness probe (too aggressive timeout), a missing config/secret, or an unhandled startup exception (bad DB connection string in a new deploy).

9. Memory usage continuously increases

Investigate: heap dump comparison over time for a growing collection (unbounded cache, listener leak). Short-term mitigation: a scheduled restart buys time; real fix is identifying and bounding the leaking collection.

10. One service causes cascading failure across the platform

Root cause: almost always a missing timeout/circuit breaker/bulkhead somewhere in the synchronous call chain, letting one slow dependency exhaust threads in every caller up the chain. Fix: audit every synchronous call for timeout + circuit breaker + bulkhead; consider whether that call should have been asynchronous (Kafka) in the first place.

34 · Scenario-Based Interview Questions

expert
"You have 20 microservices and one is causing cascading failures. What do you do?"

Immediate: identify the failing service via tracing/metrics, confirm whether circuit breakers isolated it (if not, that's the real root cause, not the failing service itself). Contain: manually trip circuit breakers or scale down traffic to the failing service if automation didn't. Long-term: audit every synchronous caller of that service for timeout/circuit-breaker/bulkhead coverage, and evaluate whether that dependency should be asynchronous instead.

"Kafka has millions of messages and consumer lag keeps increasing. How do you troubleshoot?"

Separate "more volume than usual" from "less consumption capacity than usual" first — check production rate and consumer group health/count. Then check if the bottleneck is partition-bound (add consumers up to partition count) or dependency-bound (a slow downstream call, usually the actual answer). Only increase partition count as a last resort, since it's a heavier, harder-to-reverse change.

"Two services need to update different databases atomically. How do you solve this?"

You generally don't get true atomicity across two independently-owned databases without 2PC (rarely worth its cost). Use a Saga instead — accept eventual consistency, design explicit compensating actions, and make every step idempotent so retries are safe.

"The business requires exactly-once processing. What does that actually mean?"

Push back gently: "exactly-once" as commonly meant is really "effectively-once" — at-least-once delivery plus idempotent processing, so duplicates are harmless even though they can occur. True exactly-once within Kafka-to-Kafka pipelines is achievable via transactions; extending it to an external database needs Outbox/CDC plus idempotent writes, not a flag you flip.

"Your API receives 50,000 requests/sec. How would you design it?"

Stateless horizontally-scaled service instances behind a load balancer, aggressive caching for read-heavy paths, async processing (Kafka) for anything that doesn't need an immediate synchronous answer, rate limiting/load shedding at the edge to protect against overload, and capacity-planned database connections/read replicas sized to the sustained (not just average) rate.

"The database can't handle increasing traffic. What are your options?"

In rough order of operational cost: add a cache in front of hot reads; add read replicas for read-heavy load; optimize the worst queries/indexes (often the actual fix); scale the instance vertically as a stopgap; only then consider sharding — a significant architectural commitment reserved for when the above genuinely aren't enough.

"How would you migrate a monolith to microservices?"

Strangler Fig, not a rewrite: identify a bounded context with clear boundaries and lower risk, extract it behind the existing API surface (clients don't notice), give it its own database, route an increasing share of traffic to it, and repeat — validating each extraction in production before moving to the next, rather than attempting a big-bang cutover.

"How would you design a payment system?"

See Part 28, Exercise 3 — lead with idempotency keys on every charge, an explicit persisted state machine per payment, PCI scope minimization via tokenization, and reconciliation against the payment processor's records as a second line of defense beyond your own event log.

Architect mental models

A monolith becomes microservices when independent deployment/scaling matters more than simplicity. Each service owns its own database — no exceptions. Communicate synchronously (REST) only when you genuinely need an answer now; otherwise publish events (Kafka) and let subscribers react independently. The dual-write problem (DB write + event publish aren't atomic) is solved with Outbox or CDC. Cross-service transactions use Saga with compensations, not 2PC. Every synchronous call needs a timeout, retry-with-backoff, circuit breaker, and bulkhead — without them, one slow dependency cascades into a platform-wide outage.

A topic is split into partitions for parallelism; order is guaranteed only within a partition, so key events by aggregate ID. Delivery is at-least-once by default — build idempotent consumers rather than fighting it. acks=all + min.insync.replicas gives durability at a latency cost, justified for financial events. Kafka transactions guarantee exactly-once within Kafka only, not across an external database.

Every distributed call can fail partially — "no response" doesn't mean "didn't happen." Design for duplicate, lost, and out-of-order messages as the normal case, not the edge case. CAP says you trade consistency for availability during a partition; PACELC says you keep trading latency for consistency even without one. Prefer eventual consistency across service boundaries and strong consistency only within a single service's own database.

A Pod is the smallest deployable unit; a Deployment keeps a desired replica count running via rolling updates. Liveness probes answer "restart me or not"; readiness probes answer "send me traffic or not" — conflating them causes bad rollouts. HPA scales replica count on load. The control plane (API server, etcd, scheduler, controller manager) continuously reconciles actual state toward desired state — that reconciliation loop is the core mental model for everything Kubernetes does.

Always work the same order: functional requirements → non-functional requirements with real numbers → capacity estimation → service decomposition and data ownership → sync vs async choices → failure handling → scaling → explicit trade-offs. Interviewers grade the reasoning path, not just the final diagram — narrate your decisions, don't just draw boxes.

Rules worth memorizing

Every service owns its data.
Sync when you need an immediate answer. Async when you need decoupling.
Timeout before retry. Retry with backoff and jitter. Never retry blindly.
Every distributed call can fail. Every message can arrive twice — design for idempotency.
Observability is not optional.
Scale horizontally whenever the service is stateless.
Prefer simple architecture before clever architecture — earn complexity with a felt problem, don't pre-adopt it.
