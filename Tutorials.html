01 · Kafka Fundamentals

beginner

Every concept in this course is taught through one running system: the E-Commerce Order Processing Platform — Order, Payment, Inventory, Shipping and Notification services, backed by Oracle and wired together with Kafka. Keep that picture in mind; it doesn't change for the rest of the course.

Why Kafka exists

Once you pass roughly five microservices calling each other synchronously, you hit the same three walls every time: a slow downstream service (Inventory) drags down an unrelated caller (Order), a crashed service loses in-flight work, and every new consumer of an event (Analytics, Fraud, Audit) means another point-to-point integration. Kafka replaces the mesh of direct calls with one durable, ordered, replayable log that any number of services can read independently, at their own pace, without the producer knowing or caring who's listening.

Kafka vs REST

REST is synchronous and point-to-point — the caller blocks and couples its uptime to the callee's. Kafka is asynchronous and decoupled — the producer commits a fact ("OrderCreated") to a durable log and moves on; consumers read it whenever they're ready. Use REST for request/response where you need an answer now; use Kafka for facts that other parts of the system need to react to, possibly hours or days later.

Kafka vs RabbitMQ / ActiveMQ

Traditional brokers delete a message once it's consumed — the queue is a mailbox. Kafka retains the message on disk for a configured retention window regardless of consumption, so ten consumer groups can each read the same event independently, and new consumers can replay history. RabbitMQ is better at complex per-message routing and priority queues; Kafka is better at high-throughput, replayable event streams.

Kafka vs database polling

Polling ("SELECT * FROM orders WHERE processed = 0") wastes cycles when idle, causes lock contention under load, and doesn't scale past one or two consumers. Kafka pushes work via a pull-based long-poll that scales horizontally with consumer groups and adds zero load to Oracle.

Kafka vs cloud queues (SQS/PubSub)

Most cloud queues delete-on-ack like traditional brokers and offer weaker ordering guarantees. Kafka's partition-level ordering and log retention make it the default choice when multiple independent teams need to consume the same event stream over time, not just once.

Why partitions exist

A single partition is a strictly ordered, single-writer-per-broker log — that ordering guarantee is exactly what prevents unlimited parallelism. Splitting a topic into N partitions lets N consumers in a group read in parallel, and lets the cluster spread write/read load across brokers. More partitions = more parallelism, at the cost of per-partition ordering only (never global topic ordering).

Why brokers exist

A broker is the unit of storage, network, and failure. Spreading partitions and their replicas across brokers means the loss of one broker doesn't lose data (replicas elsewhere) or availability (another replica becomes leader).

Partition assignment & leader election

For each partition, one replica is elected leader — all reads and writes for that partition go through it. The others are followers that replicate the leader's log. If the leader's broker dies, the controller promotes an in-sync follower to leader.

Consumer partition assignment

Within a consumer group, the group coordinator assigns each partition to exactly one consumer. If consumers > partitions, the excess consumers sit idle. This is why partition count is a hard ceiling on consumer parallelism.

acks=0 vs acks=1 vs acks=all

acks=0

Fire-and-forget. Producer doesn't wait for any broker confirmation. Fastest, but a broker restart can silently lose the record. Fine for metrics you can afford to lose, never for payments.

acks=1

Waits for the partition leader to write to its own log, not for followers. Fast, but if the leader dies before followers replicate, the record is lost even though the producer thought it succeeded.

acks=all (-1)

Waits for all in-sync replicas (bounded by min.insync.replicas) to acknowledge. Strongest durability, highest latency. This is the only safe setting for order and payment events.

05 · Partitioning Strategy

intermediate

The partitioner decides which lane a record travels down. Kafka guarantees order only within a partition — this single fact drives most partition-key decisions you'll ever make.

Key-based (default when a key is present)

hash(key) % numPartitions. Every record with the same key always lands on the same partition, so all events for one entity stay in arrival order relative to each other.

Round robin / sticky (no key)

Spreads records evenly across partitions to balance load, but gives up any ordering guarantee between records.
Applied to the order platformEvery OrderCreated, PaymentCompleted, and OrderShipped event is keyed by customerId (or orderId, depending on the aggregate). Customer 1001's events all route to the same partition, so a consumer reading that partition sees them in the order they happened — but two different customers' events can legitimately interleave or even appear "out of order" relative to each other, and that's fine because nothing depends on cross-customer ordering.

Custom partitioner — used when the default key hash doesn't match a business rule, e.g. routing VIP customers to a dedicated set of partitions for isolation:

public class VipAwarePartitioner implements Partitioner {
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                        Object value, byte[] valueBytes, Cluster cluster) {
        int numPartitions = cluster.partitionCountForTopic(topic);
        if (isVipCustomer((String) key)) {
            return Math.abs(key.hashCode()) % VIP_PARTITION_COUNT; // reserved lanes
        }
        return VIP_PARTITION_COUNT + (Math.abs(key.hashCode()) % (numPartitions - VIP_PARTITION_COUNT));
    }
}

Manual commit: sync vs async

commitSync()

Blocks until the broker confirms the commit. Safer — you know the offset moved — but adds latency per batch.

commitAsync()

Fire-and-forget with a callback for errors. Higher throughput, but a failed async commit is easy to silently miss; always pair with a final commitSync() on shutdown.

07 · Consumer Groups & Rebalancing

intermediate
Topic order-events: P0 P1 P2 P3
↓ assigned across group inventory-service
C1 → P0 C2 → P1 C3 → P2 C4 → P3
A 5th consumer (C5) joins the group

Group coordinator triggers a rebalance. With only 4 partitions, C5 gets none and sits idle until another consumer leaves or partitions increase. Consumer count can never exceed partition count for useful parallelism.

A consumer leaves cleanly

It sends a LeaveGroup request; the coordinator immediately reassigns its partitions to remaining members.

A consumer crashes

No clean leave — the group only notices after missed heartbeats exceed session.timeout.ms. Its partitions are unread until that timeout fires, meaning a real (if short) processing gap.

A consumer is just slow (not crashed)

If it can't call poll() again within max.poll.interval.ms, the coordinator treats it as dead and rebalances even though the process is alive — a classic cause of "phantom" rebalance loops when processing time is unpredictable.

A new partition is added to the topic

Existing keys don't automatically move — only new records hashing to the new partition land there. This can quietly break "same key always same partition" assumptions if you repartition a live topic; plan partition count up front where ordering matters.

Eager vs cooperative rebalancing, and static membership

Eager rebalance

Every consumer gives up all its partitions and the group reassigns from scratch — simple but causes a full stop-the-world pause across the group.

Cooperative (incremental) rebalance

Only the specific partitions that need to move are revoked; everyone else keeps processing uninterrupted. This is the default strategy in modern clients and should be preferred.

Static membership

Setting group.instance.id lets a consumer rejoin after a brief restart (deploy, pod reschedule) without triggering a rebalance at all, as long as it returns inside session.timeout.ms.

Scenario: commit before vs after processing

Commit before processing, then crash → offset already moved, but the work never happened → the message is silently skipped (message loss from the application's point of view).

Commit after processing, then crash before the commit lands → on restart the consumer re-reads the same record and reprocesses it (duplicate processing). This is why "at-least-once" is the natural default — you must design consumers to be idempotent rather than trying to engineer offset commits into never producing a duplicate.

09 · Delivery Semantics & Idempotency

intermediate

At most once

Commit offset before processing. Payment example: a crash after commit but before charging the card means the payment is simply never made. Cheap, but unacceptable for money.

At least once

Commit offset after processing. A crash between processing and commit means the payment can be charged twice on redelivery. This is Kafka's practical default — solved with idempotent consumers, not avoided.

Exactly once

Requires an idempotent producer + transactions + idempotent (or transactional) consumers working together end-to-end. Achievable Kafka-to-Kafka; genuinely hard — not free — when a non-Kafka system like Oracle is in the loop.

Implementing idempotency in the Payment Service

Given a Kafka redelivery of PAY-10001, the application — not Kafka — must guarantee it's charged once:

Database unique constraint

A unique index on payment_id in Oracle. The second insert attempt throws a constraint violation, which the consumer catches and treats as "already handled" — the strongest guarantee when a DB write is already happening anyway.

Idempotency / dedup table

A dedicated table of processed message IDs checked before doing the real work — useful when the main write isn't naturally unique-constrained (e.g. calling an external payment gateway).

Redis (SETNX with TTL)

Fast, in-memory dedup check for high-throughput paths where a DB round-trip per check is too slow. Trade-off: Redis eviction/TTL means the dedup window isn't infinite.

Kafka's idempotent producer

Prevents duplicates caused by the producer retrying a send (e.g. a network blip after the broker actually wrote the record). It does not protect against the application publishing the same business event twice — that's still your job.

11 · The Database + Kafka Problem, Outbox, and CDC

advanced
The dual-write problemOrder Service does two independent things: commit a row to Oracle, then publish to Kafka. There is no distributed transaction spanning both by default. If Oracle commits but the Kafka publish fails (network blip, broker down), the order exists but no downstream service ever hears about it. If you reverse the order and publish first, you can end up with an event for an order that never actually committed. Distributed transactions across heterogeneous systems (XA/2PC) are technically possible but operationally painful and rarely used in modern architectures — hence outbox and CDC.

Outbox Pattern

Because the order row and the outbox row are written in the same local Oracle transaction, they either both commit or both roll back — no distributed transaction needed. A separate publisher (polling the table, or backed by CDC) then reliably ships outbox rows to Kafka and marks them sent.

@Entity
class OutboxEvent {
    @Id @GeneratedValue UUID id;
    String aggregateType;   // "Order"
    String aggregateId;     // orderId
    String eventType;       // "OrderCreated"
    @Lob String payload;      // JSON
    Instant createdAt;
    boolean published = false;
}

@Service
class OrderService {
    @Transactional // one local Oracle transaction — atomic by construction
    public void createOrder(OrderRequest req) {
        Order order = orderRepository.save(new Order(req));
        outboxRepository.save(new OutboxEvent(
            "Order", order.getId(), "OrderCreated", toJson(order)));
        // no Kafka call here — the publisher handles that out-of-band
    }
}

@Scheduled(fixedDelay = 500)
void publishPendingOutboxEvents() {
    for (OutboxEvent e : outboxRepository.findByPublishedFalse()) {
        kafkaTemplate.send("order-events", e.getAggregateId(), e.getPayload())
            .whenComplete((r, ex) -> { if (ex == null) markPublished(e); });
    }
}

CDC tails the database's own transaction log (no polling, near-real-time) and turns every row change into an event automatically — including changes made outside your service, like a DBA hotfix. Thread-safe wrapper around a KafkaProducer for sending records, returning a CompletableFuture you can chain success/failure handling onto.

Declarative consumer binding to a topic + group id; Spring manages the poll loop, threading, and (optionally) manual acknowledgment for you.

Declarative retry-then-DLQ: retries a failing record N times with backoff, then republishes it to a <topic>.DLT topic instead of blocking the partition forever.
@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template);
    var backoff = new ExponentialBackOff(1000L, 2.0);
    backoff.setMaxInterval(30000L);
    DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, backoff);
    handler.addNotRetryableExceptions(IllegalArgumentException.class); // poison messages go straight to DLQ
    return handler;
}

13 · Kafka Transactions & Exactly-Once

advanced

A transactional producer wraps a set of sends (and optionally a consumer offset commit) in an atomic unit via transaction.id, initTransactions(), beginTransaction(), commitTransaction()/abortTransaction(). Consumers reading with isolation.level=read_committed never see records from an aborted transaction.

producer.initTransactions();
try {
    producer.beginTransaction();
    producer.send(new ProducerRecord<>("inventory-events", orderId, reservedEvent));
    producer.send(new ProducerRecord<>("audit-events", orderId, auditEvent));
    producer.commitTransaction(); // both records become visible atomically
} catch (KafkaException e) {
    producer.abortTransaction(); // neither record becomes visible
}
Kafka-to-Kafka exactly-once ≠ Kafka+Oracle exactly-onceKafka transactions give you exactly-once within Kafka — a "consume, transform, produce" pipeline (e.g. Kafka Streams) can commit its output records and its consumer offset atomically. They do not extend to an Oracle write in the same consumer. If a listener writes to Oracle and then Kafka, or vice versa, you're back to the dual-write problem — solved with the Outbox Pattern, not with Kafka transactions. Do not tell an interviewer "Kafka gives exactly-once with the database" without this caveat; it's the single most common architect-level mistake candidates make.

15 · "What Happens If…?"

advanced
Producer crashes mid-send

If the batch hadn't been acknowledged yet, on restart the producer resends (idempotent producer prevents a duplicate landing twice for the same producer session). If it crashed after the broker wrote but before the ack reached it, the write already happened — the app just doesn't know that yet, which is a normal at-least-once condition.

A follower broker crashes

It drops from the ISR. Writes continue as long as the remaining ISR still meets min.insync.replicas. No consumer-visible impact.

The leader broker crashes

Brief unavailability for that partition while the controller elects a new leader from the ISR; in-flight requests to the old leader fail and the client's metadata refresh routes to the new leader.

Cluster loses one broker vs two brokers (RF=3)

Losing one broker: fully tolerated with min.insync.replicas=2 — no data loss, writes continue. Losing two brokers simultaneously: any partition whose remaining single replica isn't enough to satisfy min.insync.replicas stops accepting acks=all writes — Kafka correctly chooses unavailability over silently under-replicating a "successful" write.

Oracle is unavailable when a consumer tries to write

The consumer should not commit the offset — it should let the exception propagate (or explicitly retry) so the same record is redelivered once Oracle recovers, at the cost of at-least-once duplicate risk that idempotent writes must absorb.

Network partition between producer and cluster

Sends time out and retry per delivery.timeout.ms; the idempotent producer's sequence numbers prevent a retried batch from being applied twice once connectivity returns.

16 · Retry & Dead Letter Topics

intermediate

DLQ

Poison message: a record that will never succeed no matter how many times it's retried (malformed payload, unrecoverable business rule violation). Retrying it indefinitely blocks the partition behind it from making progress — route it to a DLQ immediately instead of retrying, which is exactly what addNotRetryableExceptions does above. Exponential vs fixed backoff: exponential backoff (as shown in the Spring Kafka example) avoids hammering a struggling downstream dependency; fixed backoff is simpler but can pile on load during an outage.

17 · Ordering Guarantees

intermediate

Kafka guarantees order within a partition only. For the order lifecycle — OrderCreated → PaymentStarted → PaymentCompleted → OrderShipped — as long as every event for the same orderId is keyed identically, they land on the same partition in the order they were produced.

How ordering breaks in practice
  • Different producers publish related events with different keys (e.g. one service keys by orderId, another by customerId) — they land on different partitions with no relative order guarantee.
  • Retries reorder: if max.in.flight.requests.per.connection > 1 without idempotence, a retried batch can land after a later batch that succeeded first.
  • Multiple consumers in a group naturally process different partitions in parallel — if your application logic assumes strict global order across all of a topic's records, parallel consumption breaks that assumption regardless of partition-level guarantees.

19 · Kafka Connect & Kafka Streams

advanced

Kafka Connect

A framework for source connectors (Oracle → Kafka via Debezium) and sink connectors (Kafka → Elasticsearch, S3, another Oracle instance). Runs as tasks distributed across workers; a Connect cluster runs in distributed mode for production (fault-tolerant, scalable) or standalone mode for local dev.

Kafka Streams

A Java library (not a separate cluster) for stream processing directly against Kafka topics. KStream is an unbounded record stream; KTable is a changelog-backed table view (latest value per key); GlobalKTable replicates the full table to every instance for join lookups. Supports windowed aggregations and stream-stream / stream-table joins with local state stores backed by a changelog topic for fault tolerance.
KStream<String, OrderEvent> orders = builder.stream("order-events");
KTable<String, Long> ordersPerCustomer = orders
    .groupBy((key, order) -> order.getCustomerId())
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5)))
    .count();

20 · Security

advanced

Encryption — SSL/TLS

Encrypts broker-client and inter-broker traffic. Table stakes for anything on a shared network.

Authentication — SASL

SASL/PLAIN (simple, needs TLS to be safe), SASL/SCRAM (salted, hashed, no external IdP needed), SASL/OAUTHBEARER (integrates with an existing OAuth/OIDC provider — common in enterprise SSO setups).

Authorization — ACLs

Fine-grained per-principal permissions: which service can produce to payment-events, which can only consume, which is denied entirely. Applies to producers, consumers, and brokers alike.

21 · Performance & Capacity Planning

advanced

Throughput levers, roughly in order of impact: partition count (parallelism ceiling), batch.size + linger.ms (fewer, bigger network round-trips), compression.type (less network/disk per byte of business data), consumer/producer concurrency, and broker disk/network capacity. Kafka's raw speed comes from sequential disk writes and the OS page cache — the log is append-only, so it avoids the random I/O that kills traditional databases under write load.

Capacity planning worked example

500,000 events/sec × 2 KB average = 1,000 MB/s raw ingest.

Daily raw storage: 1,000 MB/s × 86,400s ≈ 84 TB/day.

With replication factor 3: ≈252 TB/day of total disk consumed across the cluster.

With 7-day retention: ≈1.76 PB total replicated storage to provision across all brokers, before headroom.

Always add 20–30% headroom for compaction/segment overhead, uneven partition skew, and burst traffic above the sustained average.

Broker metrics

CPU, disk, network, under-replicated partitions, offline partitions — under-replicated partitions climbing is usually the first sign of broker trouble

Consumer lag is the gap between the log end offset and the committed offset — it's the queue of unread work. It grows when production outpaces consumption capacity. Fixes, roughly in order of how often they're the actual bottleneck: optimize per-record processing (usually a slow Oracle call), increase consumers up to the partition count, only then increase partition count itself (a heavier operational change), or batch downstream writes instead of one DB call per record.

23 · Kubernetes & Disaster Recovery

expert

Kafka on Kubernetes

Brokers run as a StatefulSet (stable network identity + storage per pod), each backed by a PersistentVolume. An operator such as Strimzi automates broker/controller lifecycle, rolling upgrades, and rack-awareness so replicas of a partition don't collapse onto the same physical zone.

Pod failure vs broker failure

A rescheduled pod reattaches to the same PVC and rejoins as the same broker identity — no data loss, just a temporary replication gap while it catches up, same as any follower restart.

24 · Design Patterns & Anti-Patterns

expert

Saga (choreography)

Each service reacts to the previous service's event and publishes its own (Order → Payment → Inventory → Shipping), with compensating events (PaymentFailed → OrderCancelled) undoing prior steps on failure. No central coordinator; simple, but the overall flow is implicit and harder to trace.

Saga (orchestration)

A dedicated orchestrator service explicitly calls each step and issues compensations. More visible and testable, at the cost of a new central component to keep highly available.

CQRS

Separate write model (Oracle, transactional) from read model (a Kafka-Streams-maintained or Elasticsearch-backed view) — lets read-heavy dashboards scale independently of the transactional path.

Event sourcing

The event log itself is the source of truth (current state is derived by replaying events), rather than events being a side effect of a separately-owned state table. Powerful but a significant design commitment — most services in this course use events as notifications, not as event sourcing.

26 · Scenario-Based Interview Questions

expert
Scenario 1 — Consumer lag jumps from 1,000 to 10 million

Check, in order: (1) Did production suddenly spike (marketing event, batch job)? (2) Did consumer count drop — a crash, a bad deploy, a rebalance storm? (3) Is one specific consumer/partition slow (hot key, hot partition) while others are fine? (4) Is the downstream dependency (Oracle) the bottleneck — check its latency and connection pool saturation. Architect-level answer: don't just add consumers reflexively — first confirm whether the bottleneck is partition-bound (need more partitions + consumers) or dependency-bound (need to fix the slow downstream call, where more consumers just move the queue).

Scenario 2 — Payments are being processed twice

Likely causes: consumer commits the offset after processing but crashes before the commit lands (classic at-least-once redelivery), or the Payment Service itself isn't idempotent on paymentId. Diagnose: check consumer group rebalance history around the incident time, check for duplicate paymentId rows in Oracle. Fix: add a unique constraint on payment_id, treat the constraint violation as "already processed" rather than an error.

Scenario 3 — Orders are missing downstream

Possible causes: producer publish failed silently (check for unhandled exceptions on send()), retention expired before a lagging consumer group caught up, a consumer committed an offset past the record without processing it (bug or manual offset reset gone wrong), or the dual-write problem if outbox/CDC isn't in place.

Scenario 4 — Messages arrive out of order

Check the partition key strategy first — if related events use different keys they land on different partitions with no relative order. Check for retries without idempotence causing batch reordering. Check whether multiple consumers are processing what the business logic incorrectly assumes is a single ordered stream.

Scenario 5 — Oracle transaction succeeds but the Kafka event is missing

Textbook dual-write problem. Fix by moving to the Outbox Pattern (event write is part of the same local Oracle transaction) or CDC (event is derived from the committed redo log, so it can't exist without the commit). Add a reconciliation job as a safety net that diffs ORDERS against published events.

Scenario 6 — Broker disk usage hits 90%

Immediate: identify the largest topics by retention × throughput, temporarily reduce retention on non-critical topics, ensure log cleanup isn't stuck. Root cause: under-provisioned capacity planning or an unbounded-retention topic that should have been compacted or time-bounded. Prevention: alerting well before 90%, and capacity planning tied to actual growth trend, not just launch-day estimates.

Scenario 7 — One consumer is much slower than the others in its group

Check for a hot partition (uneven key distribution funneling disproportionate volume there), a slow downstream call unique to that consumer's workload (e.g. it happens to process the largest customer's orders), or resource starvation on that specific pod/instance. This is a common trigger for repeated rebalances if the slow consumer keeps missing max.poll.interval.ms.

27 · System Design Interview — High-Scale Order Processing

architect

"Design a Kafka-based order platform for 10M orders/day, peak 50,000 orders/sec, 99.99% availability, no duplicate payments, 30-day event retention, Oracle as system of record."

Capacity estimation

10M orders/day ≈ 116 orders/sec average, but the stated peak of 50,000/sec is the number to design for — burst capacity, not the average, sizes your partitions and brokers. Assume each order fans out to ~4 downstream events (created, paid, reserved, shipped) → design headroom for ~200,000 events/sec at peak across all topics combined.

Partition & topic strategy

Separate topics per event type (order-created, payment-completed, …) rather than one giant topic, so each consumer group only subscribes to what it needs. Partition count sized well above current peak consumer parallelism needs (e.g. 60–100 partitions per high-volume topic) since increasing partitions later is disruptive to key-based ordering. Key every event by orderId so the full order lifecycle stays ordered per order.

Replication & availability

Replication factor 3, min.insync.replicas=2, acks=all on financial topics, multi-AZ broker placement with rack awareness so all 3 replicas of a partition are never in the same AZ. This tolerates one full AZ outage without data loss or write unavailability.

No duplicate payments

Idempotent producer (prevents producer-retry duplicates) + unique constraint on payment_id in Oracle (prevents application-level duplicate processing from at-least-once redelivery) + Outbox Pattern (prevents the dual-write problem from ever creating a phantom or missing payment event in the first place).

Failure handling, retry, DLQ

Exponential backoff retry for transient failures (Oracle connection blip, downstream timeout), immediate DLQ routing for non-retryable exceptions (validation failures), and a reconciliation job comparing ORDERS against published outbox events to catch anything that slipped through.

Trade-offs to state explicitly

acks=all costs latency for durability — justified for payment/order topics, probably overkill for a high-volume clickstream/analytics topic where acks=1 is a reasonable trade. 30-day retention at 200K events/sec peak (using average, not peak, for storage math) is a real storage cost — quantify it rather than hand-waving, using the capacity formula from Section 21.

29 · Troubleshooting Guide

expert
Under-replicated partitions climbing

Symptoms: ISR shrinking, replication lag alerts. Likely causes: a broker under CPU/disk/network pressure, a broker down. Diagnose: kafka-topics.sh --describe --under-replicated-partitions, broker resource metrics. Fix: restore the struggling broker's resources or replace it; prevent with per-broker capacity headroom and alerting well before saturation.

Rebalance loop

Symptoms: consumer group continuously reassigning, throughput near zero. Cause: processing time exceeding max.poll.interval.ms repeatedly. Fix: lower max.poll.records, speed up per-record processing, or legitimately raise the interval if the work is unavoidably slow (batch jobs).

Serialization / deserialization errors

Cause: schema mismatch between producer and consumer, or a non-Avro/JSON payload hitting a strict deserializer. Fix: enforce Schema Registry compatibility checks at publish time so incompatible schemas never reach the topic in the first place; route unreadable records to a DLQ rather than crashing the consumer.

Producer timeouts

Cause: broker overloaded, network issue, or acks=all waiting on a slow/down replica. Diagnose: broker request latency metrics, ISR health. Fix: address the underlying broker/network issue; tune delivery.timeout.ms only after confirming it isn't masking a real capacity problem.

Oracle connection bottleneck under Kafka load

Symptoms: consumer lag grows even though Kafka itself is healthy. Cause: consumer threads outnumber the Oracle connection pool, or per-record DB writes aren't batched. Fix: batch writes, tune connection pool size to match consumer concurrency, add a write-behind cache where eventual consistency is acceptable.

Architect Cheat Sheet
Roadmap

Kafka is a distributed, durable, replayable log. A topic is split into partitions for parallelism; order is guaranteed only within a partition. Each partition has a leader and replicas; acks + min.insync.replicas control the durability/latency trade-off. Consumer groups split partitions among consumers for parallel reads. Delivery is at-least-once by default — build idempotent consumers, don't fight it. The dual-write problem (DB + Kafka) is solved with the Outbox Pattern or CDC, not with hope.

Add to the 10-minute version: producer internals (serialize → batch → partition → network → ack), consumer internals (fetch → deserialize → process → commit), rebalancing (eager vs cooperative), offset semantics (commit-before vs commit-after trade-offs), Kafka transactions and their real scope (Kafka-to-Kafka, not Kafka+Oracle), replication/ISR mechanics, Schema Registry compatibility modes, retry/DLQ design, and the core anti-patterns (single partition, no DLQ, poor partition key, treating Kafka as a database).
