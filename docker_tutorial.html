Chapter 01

Introduction to Docker

What Docker is, the problem it solves, how it differs from virtual machines, and the vocabulary you'll need for everything that follows.

Learning Mode — reveal explanations progressively (simple → technical → production → interview)

What is Docker?

Docker is an open-source platform that lets developers build, package, ship, and run applications inside lightweight, portable, self-sufficient units called containers. A container bundles application code together with all of its dependencies — libraries, binaries, configuration, and runtime — so it behaves identically wherever it runs: a laptop, a test server, or a production cloud environment.

Docker was released in 2013 by Solomon Hykes and became the industry standard for containerization because it made existing Linux container technology (cgroups, namespaces, union filesystems) easy to use through a simple CLI and a well-defined image format.

Analogy
Think of a container like a shipping container in the physical world. It can hold anything — furniture, electronics, food — and move by ship, train, or truck without being unpacked. A Docker container can hold any application and run on any machine with Docker installed, without anyone needing to know what's inside.

Technical explanation

Under the hood, a container is a process (or group of processes) on the host, isolated using Linux namespaces (PID, network, mount, user, UTS) and resource-bounded using cgroups, running against a filesystem assembled from stacked, read-only image layers plus one writable layer.

Production implication

Because the image is immutable and built once, the exact artifact tested in CI is the exact artifact deployed to production — eliminating an entire class of "worked in staging" failures.

Interview question

"What actually is a container — is it a lightweight VM?" No: a container is an isolated process on the host kernel, not a separate virtualized kernel. That distinction is the most commonly misunderstood Docker fact in interviews.

Why Docker? The Problem It Solves

Before containers, the most common complaint among developers was: "It works on my machine!" Applications often failed when moved from a laptop to a test server or production because of differences in OS versions, installed library versions, environment variables and config files, or missing dependencies.

Docker solves this by bundling the application with its entire runtime environment into an image, built once and run identically anywhere Docker is installed.

Images, Containers & Registries

Images are built from a series of read-only layers. Each Dockerfile instruction (e.g. RUN, COPY) creates a new layer. Layers are cached and shared between images, saving disk space and speeding up builds.

When you run an image, Docker adds a thin writable layer on top — this becomes the container. Any changes made while it runs are written to this layer, and it's destroyed when the container is deleted (unless a volume was used).

A registry stores and distributes images. Docker Hub is the default public registry; organizations often run private registries too (AWS ECR, Google Artifact Registry, Azure ACR, or self-hosted Harbor/Registry).

How Docker Works Internally

On Linux, Docker leverages native kernel features directly:

Namespaces

Provide isolation for processes, networking, mount points, users, and hostnames — each container believes it has its own isolated system.

Control groups (cgroups)

Limit and account for resource usage — CPU, memory, disk I/O — per container.

Union filesystems (OverlayFS)

Combine multiple layers into a single, efficient filesystem view.

On Windows, since these are Linux kernel features, Docker Desktop runs a lightweight virtualized Linux environment via WSL2 (a real Linux kernel supplied by Microsoft) to host the daemon and containers, while giving you a seamless Windows-native CLI experience.

Chapter 05

Dockerfiles In-Depth

Anatomy of a Dockerfile

A Dockerfile is a plain text script of instructions that Docker reads top-to-bottom to build an image. Each instruction adds a new layer.

dockerfile
# Base image to start from
FROM node:18-alpine

# Metadata
LABEL maintainer="dev@example.com"

# Set working directory inside the container
WORKDIR /app

# Copy dependency manifests first (better layer caching)
COPY package*.json ./

# Install dependencies
RUN npm install --production

# Copy the rest of the application source
COPY . .

# Document the port the app listens on
EXPOSE 3000

# Define environment variable
ENV NODE_ENV=production

# Command that runs when the container starts
CMD ["node", "server.js"]
Easy way to remember — core flow
F‑W‑C‑R‑C: FROM → WORKDIR → COPY → RUN → CMD

All Dockerfile Instructions Explained

Click an instruction to expand its purpose, syntax, example, and production recommendation.

CMD vs ENTRYPOINT

One of the most common points of confusion for beginners.

  • CMD provides default arguments that can be completely overridden by whatever is passed after the image name in docker run.
  • ENTRYPOINT configures the container to run as a fixed executable — arguments passed to docker run are appended to it rather than replacing it.

They're often combined: ENTRYPOINT defines the binary, CMD defines default arguments.

dockerfile
ENTRYPOINT ["python", "app.py"]
CMD ["--port", "8080"]

docker run myimage

Resulting command: python app.py --port 8080 — CMD's default argument is used.

docker run myimage --port 9090

Resulting command: python app.py --port 9090 — the CLI argument replaces CMD's default, but ENTRYPOINT's binary stays fixed.

Build Context & .dockerignore

When you run docker build ., the . is the build context — the set of files sent to the Docker daemon. Everything in this directory (unless excluded) is sent, so keep it lean.

Multi-Stage Builds

Multi-stage builds let you use multiple FROM statements in one Dockerfile. Each stage can use a different base image, and you selectively copy only the artifacts you need into the final stage — producing much smaller, more secure production images.

Source
↓
Build stage
node + npm + dependencies → npm run build
↓
Production stage
nginx
↓
Small production image
dockerfile — React app served by Nginx
# ---- Stage 1: Build ----
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# ---- Stage 2: Production ----
FROM nginx:alpine
COPY --from=builder /app/build /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

The final image contains only Nginx and the compiled static files — not Node.js, npm, or the ~200MB of build tooling and node_modules. This can shrink an image from 1GB+ down to under 30MB, reducing image size, attack surface, and production dependencies.

dockerfile — Go binary
FROM golang:1.22 AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /app main.go

FROM scratch
COPY --from=builder /app /app
ENTRYPOINT ["/app"]

Best Practices

  • Use small base images (alpine, slim variants) to reduce size and attack surface.
  • Order instructions from least to most frequently changing to maximize layer cache reuse — copy dependency manifests and install dependencies before copying full source.
  • Combine RUN commands with && to reduce layers and clean up in the same layer.
  • Pin specific base image versions (avoid latest in production) for reproducible builds.
  • Don't run as root — create and switch to a non-root user with USER.
  • Use multi-stage builds to keep final images minimal.
  • Use a .dockerignore file to avoid bloated build contexts and secret leakage.
  • Use COPY over ADD unless you specifically need ADD's URL/extraction features.
  • Set explicit CMD/ENTRYPOINT so the image is runnable without extra flags.
  • Add HEALTHCHECK so orchestrators can detect unhealthy containers.
dockerfile — non-root user
FROM node:18-alpine
WORKDIR /app
COPY . .
RUN npm install --production && \
    addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser
CMD ["node", "server.js"]
bash — build variants
docker build -t myapp:1.0 .
docker build --build-arg VERSION=2.1 -t myapp:2.1 .
docker build --target builder -t myapp:builder-stage .
docker build --no-cache -t myapp:1.0 .
Chapter 06

Data Persistence: Volumes & Bind Mounts

By default, data written inside a container's writable layer is lost when the container is removed. Docker offers three mechanisms to persist data outside a container's lifecycle.

Stored in a part of the host filesystem managed by Docker (/var/lib/docker/volumes/ on Linux). Preferred because Docker manages their lifecycle, they work identically across OSes, and they can be shared safely among multiple containers.

bash
docker volume create mydata
docker volume ls
docker volume inspect mydata
docker volume rm mydata
docker volume prune

docker run -d --name mysql-db \
  -e MYSQL_ROOT_PASSWORD=secret \
  -v mydata:/var/lib/mysql \
  mysql:8.0

Even if mysql-db is removed, the volume mydata and its contents remain, and can be reattached to a new container.

Bind mounts map an exact path on the host machine to a path inside the container — extremely useful during development since host file changes are reflected inside the container immediately (hot-reload).

bash
# Windows PowerShell - mount current directory into /app
docker run -it --rm -v ${PWD}:/app -w /app node:18-alpine sh

# Long-form --mount syntax (more explicit)
docker run -it --rm \
  --mount type=bind,source="$(pwd)",target=/app \
  -w /app node:18-alpine sh

# Read-only bind mount
docker run -v ${PWD}/config:/etc/app/config:ro myapp
Windows tip
For best bind-mount performance, store project files inside the WSL2 Linux filesystem (e.g. \\wsl$\Ubuntu\home\username\project) rather than the Windows C:\ drive, and run Docker commands from within the WSL2 terminal.

A tmpfs mount stores data only in host memory, never on disk. It disappears when the container stops — useful for secrets or temporary caches.

bash
docker run -d --tmpfs /app/tmp:rw,size=64m myapp

Bridge Networks & Port Publishing

By default, every standalone container connects to the default bridge network. Containers on it can reach each other by IP, but not by name — that requires a custom network.

bash
# Format: -p host:container
docker run -d -p 8080:80 nginx

# Publish to a specific host interface
docker run -d -p 127.0.0.1:8080:80 nginx

# Let Docker pick a random available host port
docker run -d -p 80 nginx
docker port <container>   # see which host port was assigned

# Publish all EXPOSE'd ports to random host ports
docker run -d -P nginx

Custom Networks & Container DNS

User-defined bridge networks are recommended for multi-container apps because Docker provides automatic DNS resolution — containers reach each other simply by container name (or Compose service name).

Container A
api
↔ app-net ↔
Container B
db
bash
docker network create app-net

docker run -d --name api --network app-net myapi:latest
docker run -d --name db  --network app-net postgres:16

# From inside the "api" container, "db" resolves automatically:
docker exec -it api ping db

Why db works but localhost doesn't: on a custom network, Docker's embedded DNS server resolves the container/service name to its private network IP. localhost only ever refers to the container's own loopback interface, never another container's.

bash — network management
docker network ls
docker network inspect app-net
docker network connect app-net web
docker network disconnect app-net web
docker network rm app-net
docker network prune

Host & None Networks

bash
# Host network - shares host's network namespace directly (Linux only)
docker run -d --network host nginx

# None network - fully isolated, no networking at all
docker run -d --network none myapp
Note
The host network driver is not supported the same way on Docker Desktop for Windows/Mac as on native Linux, because containers run inside a Linux VM. Prefer bridge networks with explicit port publishing on Windows.
Chapter 08

Environment Variables & Configuration

The standard way to configure containerized applications without rebuilding the image — following the "12-factor app" methodology.

bash — setting variables at runtime
# Single variable
docker run -e NODE_ENV=production myapp

# Multiple variables
docker run -e NODE_ENV=production -e PORT=3000 myapp

# Load variables from a file
docker run --env-file .env myapp
.env
NODE_ENV=production
PORT=3000
DATABASE_URL=postgres://user:pass@db:5432/mydb
API_KEY=supersecretkey
⚠ Security note
Never bake secrets (passwords, API keys) directly into a Dockerfile with ENV or ARG — they remain visible in the image's layer history via docker history. Prefer runtime environment variables, --env-file, Docker secrets, or a secrets manager.
dockerfile — defaults + build-time override
# Dockerfile: default values
ENV PORT=8080
ENV NODE_ENV=production
EXPOSE $PORT

# Overriding at build time with ARG
ARG APP_VERSION=1.0
ENV APP_VERSION=$APP_VERSION

# Build command
docker build --build-arg APP_VERSION=2.5 -t myapp .

Docker Compose

Real applications rarely consist of a single container. Compose defines an entire multi-container setup declaratively in one YAML file, then brings it all up (or down) with one command.

Compose File Structure

yaml — docker-compose.yml
version: "3.9"
services:
  web:
    build: .
    ports:
      - "3000:3000"
    environment:
      - NODE_ENV=production
    depends_on:
      - db
    networks:
      - app-net

  db:
    image: postgres:16
    restart: always
    environment:
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: apppass
      POSTGRES_DB: appdb
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - app-net

  redis:
    image: redis:alpine
    networks:
      - app-net

volumes:
  db-data:

networks:
  app-net:
    driver: bridge

Compose CLI Commands

bash
docker compose up            # create and start all services (foreground)
docker compose up -d         # start in detached (background) mode
docker compose up --build    # rebuild images before starting
docker compose down          # stop and remove containers, networks
docker compose down -v       # also remove named volumes
docker compose ps            # list running services
docker compose logs -f       # stream logs from all services
docker compose logs -f web   # stream logs from just the "web" service
docker compose exec web sh   # open a shell inside the running "web" service
docker compose build         # build/rebuild images without starting
docker compose stop          # stop services without removing them
docker compose restart web   # restart a single service
docker compose config        # validate and view the resolved configuration

Chapter 13

Introduction to Container Orchestration (Docker Swarm)

While Compose is great for a single host, production systems often need to run containers across multiple machines with automatic scaling, load balancing, and self-healing. Swarm is Docker's built-in orchestration tool for this.

Architect note
Kubernetes is the more widely adopted industry alternative to Swarm, but Swarm is simpler to start with and ships with Docker itself — as noted directly in the source material.

bash — initializing a swarm
# On the manager node
docker swarm init --advertise-addr <MANAGER-IP>

# Join a worker node (uses the token printed by swarm init)
docker swarm join --token <TOKEN> <MANAGER-IP>:2377
bash — deploying a service
docker service create --name web --replicas 3 -p 8080:80 nginx:alpine
docker service ls
docker service scale web=5
docker service ps web
docker service rm web
bash — deploying a full stack
docker stack deploy -c docker-compose.yml mystack
docker stack services mystack
docker stack rm mystack
